This technical review documents the current individual-earnings specification, its source variables, sample restrictions and validation checks.

1. Exact definition used

The parent regressor is the sum of the recorded mother’s own earnings and recorded father’s own earnings. The child outcome is the child’s own earnings, using the same definition. Both generations are measured in the same income year.

The available PSID generated measures used here are labor income excluding farm and unincorporated-business income. They include wages/salaries and listed job-related components, including bonuses, overtime, tips and commissions. They are not total personal income: pensions, Social Security, capital income, and the excluded business/farm income are not included. This is an explicitly scoped earnings-based implementation, not a claim that total individual income has been constructed. The role-specific variables can be assigned to current reference persons and spouses; other family members’ individual income is not constructed in this run.

The codebooks for all four waves were checked for this same definition. PSID has already assigned missing values in these generated labor-income measures; no additional income imputation was performed here.

3. SQL joins and selection

  1. Exclude unknown mother/father identifiers. Person number 999 means identity unclear, not a valid parent ID. An initial validation caught three links where both parents had this unknown code; the explicit filter now handles them.
  2. Join each person’s current family ID to the Family File on family ID and wave together.
  3. Assign rp_earnings to relationship 10/sequence 1; assign sp_earnings to relationship 20 or 22/sequence 2. A mother can be either role; a father can be either role. Sex is not used as a shortcut for household role.
  4. Join the child, mother and father using their two-field identifiers in the same wave.
  5. Add mother and father earnings once each. They may share a household or live separately. Never add household totals and never substitute the current spouse for the recorded biological parent.
  6. Require all three to be observed adults (interview ages 19–110) with valid earnings. A missing parent is excluded, never converted to zero. A recorded zero earner is retained at this stage.
  7. For both log–log OLS and rank–rank regressions, require positive child earnings and combined parental earnings, not positive earnings for every parent separately. Keep the same children in all four waves.

4. Nominal income and averages

For each year:

Xit=Mit+Fit,Yit=Cit.X_{it}=M_{it}+F_{it},\qquad Y_{it}=C_{it}.

SQL forms arithmetic averages over 2016, 2018, 2020, 2022:

X¯i=14∑t(Mit+Fit),Y¯i=14∑tCit.\overline X_i=\frac14\sum_t(M_{it}+F_{it}),\qquad \overline Y_i=\frac14\sum_t C_{it}.

Logs are taken after averaging. There is no CPI adjustment, interpolation, winsorization, or additional imputation in the main results.

Your inflation argument holds within a single year. Dividing both X and Y by the same annual price index shifts the log intercept without changing the slope. I verified numerically that all four single-year slopes are unchanged to numerical precision. It also leaves within-year ranks unchanged.

For multi-year averages, each year’s conversion factor differs. Nominal averaging weights later price levels differently, so it is not generally equivalent to real averaging. As a diagnostic only, the identical sample’s averaged IGE is 0.117448 nominal versus 0.115382 real. The primary tables below use nominal income as requested.

5. Regression specification and results

log⁡Ci=α+βlog⁡(Mi+Fi)+εi.\log C_i=\alpha+\beta\log(M_i+F_i)+\varepsilon_i.

The averaged version substitutes the corresponding arithmetic averages before taking logs. All models have an intercept and no age or other controls, and are unweighted. Main confidence intervals cluster by connected parental networks: children sharing either recorded parent are in the same cluster, including half-siblings. There are 278 clusters.

6. Bonus: rank–rank regression

Richild=a+bRiparents+ui.R_i^{child}=a+bR_i^{parents}+u_i.

This is meaningful as a relative mobility measure, distinct from a dollar elasticity. Higher parent rank predicts higher child rank when the slope is positive. For the average-income main sample, a 10-percentile-point parent difference is associated with approximately 2.38 percentile points in child rank. It is not a causal effect.

SQL computes percentile midranks separately for each generation and measurement. Tied incomes get the average tied rank:

Ri=100midranki−0.5N.R_i=100\frac{\text{midrank}_i-0.5}{N}.

For the multi-year model, first average nominal earnings, then rank those averages. Do not average yearly ranks. Parents are ranked across the child observations, so siblings receive tied parent ranks. These are ranks within our selected pooled-age sample, not national ranks or birth-cohort-specific ranks. Rank–rank approaches are used in intergenerational mobility research, but this small selected sample does not reproduce that research’s population design.

7. Checks performed and remaining limits

  • Checked all four codebooks for consistent earnings definitions and the raw import column positions.
  • Recorded SHA-256 hashes and counts; raw files remain unchanged.
  • Checked unique individual-wave and family-wave keys, distinct parents and no self-parent links.
  • Enforced one child-wave row after matching and exactly four observations per main child.
  • Verified every parental sum equals the separately matched mother plus father.
  • Independently recalculated SQL averages in Python; verified average sums equal sums of parent averages.
  • Independently recalculated SQL tied ranks in Python on the same positive-income sample.
  • Verified single-year slopes are invariant to a common CPI deflator.

These checks verify data processing, not causal identification or the absence of selection bias. This analysis does not empirically isolate life-cycle bias. Four recent income years cannot reveal lifetime earnings; both parents’ observation and positive-earnings restrictions particularly affect older families. Total personal income, farm/business earnings, pensions and capital income are not represented in this earnings definition. If the intended concept is total income, that requires a separately documented construction before finalizing the blog.

Complete SQL used in this rerun

-- Revised analysis: individual nonfarm/non-business labor income, nominal dollars.
-- The PID file establishes parentage. Cross-year records locate each person.
CREATE TABLE links AS
SELECT PID2 child_id68, PID3 child_pn,
       PID4 mother_id68, PID5 mother_pn, PID23 father_id68, PID24 father_pn
FROM pid WHERE PID4>0 AND PID5 BETWEEN 1 AND 995
           AND PID23>0 AND PID24 BETWEEN 1 AND 995;
-- Person number 999 means the parent was reported but identity is unclear.
CREATE UNIQUE INDEX link_child ON links(child_id68, child_pn);

-- Correctly assign a person's OWN income from their role, not family total.
CREATE TABLE personal AS
SELECT p.*, f.income_year,
       CASE WHEN p.relationship=10 AND p.sequence=1 THEN f.rp_earnings
            WHEN p.relationship IN (20,22) AND p.sequence=2 THEN f.sp_earnings
       END AS earnings
FROM person_year p
JOIN family_year f ON p.wave=f.wave AND p.family_id=f.family_id
WHERE p.sequence BETWEEN 1 AND 20;
CREATE UNIQUE INDEX personal_key ON personal(id68,pn,wave);

CREATE TABLE matched AS
SELECT l.*, ch.wave, ch.income_year,
       ch.age child_age, mo.age mother_age, fa.age father_age,
       mo.family_id mother_family_id, fa.family_id father_family_id,
       ch.earnings child_income, mo.earnings mother_income, fa.earnings father_income,
       mo.earnings+fa.earnings parent_income
FROM links l
JOIN personal ch ON ch.id68=l.child_id68 AND ch.pn=l.child_pn
JOIN personal mo ON mo.id68=l.mother_id68 AND mo.pn=l.mother_pn AND mo.wave=ch.wave
JOIN personal fa ON fa.id68=l.father_id68 AND fa.pn=l.father_pn AND fa.wave=ch.wave;

CREATE TABLE adult_observed AS
SELECT * FROM matched
WHERE child_age BETWEEN 19 AND 110
  AND mother_age BETWEEN 19 AND 110 AND father_age BETWEEN 19 AND 110
  AND child_income BETWEEN 0 AND 9999997
  AND mother_income BETWEEN 0 AND 9999997
  AND father_income BETWEEN 0 AND 9999997;

CREATE TABLE positive AS
SELECT * FROM adult_observed WHERE child_income>0 AND parent_income>0;

CREATE TABLE balanced AS
SELECT p.* FROM positive p
JOIN (SELECT child_id68,child_pn FROM positive
      GROUP BY child_id68,child_pn HAVING COUNT(DISTINCT wave)=4) b
USING(child_id68,child_pn);
CREATE UNIQUE INDEX balanced_key ON balanced(child_id68,child_pn,wave);

CREATE TABLE averaged AS
SELECT child_id68,child_pn,mother_id68,mother_pn,father_id68,father_pn,
       AVG(mother_income) mother_income, AVG(father_income) father_income,
       AVG(parent_income) parent_income,AVG(child_income) child_income,
       COUNT(*) n_years
FROM balanced
GROUP BY child_id68,child_pn,mother_id68,mother_pn,father_id68,father_pn
HAVING COUNT(*)=4;

-- Rank-rank bonus on the exact same positive balanced sample.
CREATE TABLE income_measures AS
SELECT CAST(income_year AS TEXT) measure,child_id68,child_pn,parent_income,child_income FROM balanced
UNION ALL
SELECT 'Four-year average',child_id68,child_pn,parent_income,child_income FROM averaged;

-- Midranks: average tied ranks, rescaled to percentiles centered in (0,100).
-- Parents are ranked across child observations; siblings retain equal parent ranks.
CREATE TABLE ranked AS
SELECT *,100.0*(RANK() OVER(PARTITION BY measure ORDER BY parent_income)
          +(COUNT(*) OVER(PARTITION BY measure,parent_income)-1)/2.0-0.5)
          /COUNT(*) OVER(PARTITION BY measure) parent_rank,
         100.0*(RANK() OVER(PARTITION BY measure ORDER BY child_income)
          +(COUNT(*) OVER(PARTITION BY measure,child_income)-1)/2.0-0.5)
          /COUNT(*) OVER(PARTITION BY measure) child_rank
FROM income_measures;
